# 0005 — 히스토리·첨부는 저장소 백엔드만의 기능이다

- 상태: 승인
- 날짜: 2026-08-20

## 맥락

전송 계약은 "버전 붙은 JSON을 읽고 compare-and-swap으로 쓴다"가 전부이고, 백엔드의
`history`/`files`는 계약이 아니라 **선택적 능력**이다 (DESIGN.md 원칙 17). 실제로는 GitHub
백엔드만 이 능력을 구현해서, 백엔드에 따라 조용히 없는 기능 — 문서 히스토리와 이미지 첨부 —
이 생겼다. 지금은 백엔드가 둘이라 괜찮지만, 능력이 늘수록 "REST 백엔드는 반쪽짜리"가 된다
([refactor-plan.md](../design/refactor-plan.md) 「남겨둔 리스크」).

## 결정

**선을 긋는다.** 히스토리·첨부는 "저장소 백엔드만의 기능"으로 문서와 UI에 명시하고, 저장소
백엔드에만 있는 능력을 더 늘리지 않는다. 새 기능이 능력을 요구하면 그 기능은 (a) 계약만으로
구현되거나 (b) 기존 두 능력처럼 저장소의 본성에서 공짜로 나오는 것(커밋이 곧 히스토리,
파일이 곧 첨부 저장소)이어야 한다.

## 검토한 대안

- **REST 백엔드에도 능력을 준다:** 히스토리는 저장하는 서버가 필요하고 첨부는 두 번째 URL이면
  되지만, 둘 다 "JSON `GET`/`PUT` 되는 주소 하나면 백엔드"라는 계약의 단순함을 깬다. 그
  단순함이 이 앱이 Firebase 경로든 자작 엔드포인트든 아무 서버에나 붙는 이유다.
- **능력 없는 UI를 일급으로 만든다:** 지금도 히스토리 패널과 이미지 붙여넣기가 이유를 말하는
  안내 문구를 띄운다. 그 이상은 없는 기능을 위한 화면을 늘리는 일이다.

## 결과

- 설정 UI의 "내 서버 / URL" 모드가 이 선을 한 문장으로 미리 안내한다 — 기능이 없어진 뒤에야
  알게 하지 않는다.
- README 기능 목록과 DESIGN.md 「알려진 한계」가 같은 선을 쓴다.
- refactor-plan.md 「남겨둔 리스크」와 PLANS.md 대기열의 해당 항목은 이 ADR로 해소됐다.
