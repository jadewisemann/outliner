# ADR-0009 — delta 동기화는 지금 하지 않고, 무엇을 포기해야 하는지를 적어 둔다

- 날짜: 2026-09-01
- 상태: **제안**. 아래 「결정」은 지금 시점의 판정이고, 사용자가 실제로 한계에 부딪히면 뒤집는다.

## 맥락

DESIGN.md 「알려진 한계」에는 "한 문서를 고치면 그 문서 전체를 올린다"라는 항목이 있고, PLANS.md
대기열 4번에는 delta 동기화가 올라 있었다. [backend-capacity.md](../research/backend-capacity.md)는
"답은 백엔드 교체가 아니라 delta 동기화다"라고까지 적었지만, 설계는 하지 않았다.

먼저 크기를 **재는** 일부터 시작했다(그 문서의 「2026-09-01 실측」). 요약하면 이렇다.

- 노드 하나는 약 **800바이트**다. id와 parent로 UUID가 두 개 들어가고 스탬프가 세 개라서,
  텍스트가 한 글자여도 이만큼의 크기가 붙는다.
- 1만 노드짜리 문서는 푸시 한 번의 크기가 **7.8 MB**(gzip 842 kB)다.
- REST 백엔드는 페이로드가 워크스페이스 전체이므로, 문서 50개짜리 워크스페이스는 **한 줄만 고쳐도
  22 MB**를 1.5초 케이던스로 올린다. **GitHub보다 REST가 먼저 문제가 된다.**

그리고 적은 비용으로 크기를 줄일 방법이 있는지도 재 보았다. `children`은 `parent`/`sort`에서
파생된 캐시(원칙 5)라서 원격에서 빼고 읽는 쪽에서 다시 만들 수 있는데, 그 몫은
**전체의 6.5%**였다. 그 정도로는 모든 문서를 한 번 다시 쓰는 커밋 소음을 치를 가치가 없어서,
그 방법은 배제했다.

## 무엇이 걸리는가

delta 동기화는 "바뀐 부분만 보낸다"는 뜻이고, 그러려면 **원격이 문서보다 작은 단위를 알아야 한다.**
지금 두 백엔드에서 그 단위는 각각 문서 파일 하나와 워크스페이스 파일 하나다. 단위를 쪼개는
순간, 문서에 명시해 둔 것 두 가지가 깨진다.

1. **"문서 하나 = 파일 하나"**: GitHub 백엔드의 값어치가 여기에 있다. 커밋 diff가 "무엇을
   고쳤는지"를 그대로 보여 주고([parity.md](../parity.md) §8), 히스토리 패널은 한 파일의 커밋
   목록이며, Markdown 미러는 문서마다 하나다 ([ADR-0007](./0007-markdown-mirror.md)).
2. **"아무 `GET`/`PUT` JSON 엔드포인트면 된다"**: 전송 계약이 능력을 요구하지 않는다는 것이
   원칙 17이고, [ADR-0005](./0005-backend-capability-line.md)가 그은 선이다.

## 검토한 설계 넷

| # | 설계 | 얻는 것 | 포기하는 것 |
|---|---|---|---|
| A | GitHub에서 큰 문서를 절 단위로 쪼갠다 (`docs/{id}/{절 id}.json`) | 큰 문서의 푸시가 고친 절만큼으로 줄어든다 | 기둥 1. 레이아웃이 두 가지가 되고, 히스토리 패널과 미러에 절을 조립하는 기능이 필요해진다 |
| B | 전송 계약에 delta를 더한다 (PATCH나 추가 전용 로그) | 두 백엔드 모두 해결된다 | 기둥 2. 서드파티 엔드포인트를 더는 그대로 연결할 수 없다 |
| C | 하지 않는다. 대신 실측을 남기고 조건을 지켜본다 | 아무것도 깨지지 않는다 | 큰 문서를 쓰는 사람에게는 아무런 답이 되지 않는다 |
| D | REST 백엔드만 문서 단위 경로로 저장한다 (`{url}/docs/{id}.json`) | **먼저 문제가 되는 쪽**이 GitHub과 같은 수준이 된다 | 기둥 2의 일부. 경로를 다루는 엔드포인트만 지원하게 된다 |

기술적으로는 D의 비용 대비 효과가 가장 크다. 경로 단위 저장은 Firebase RTDB도 지원하고, 이번에
만든 `server/outliner-server.mjs`도 곧 지원할 수 있다. 다만 조건이 "URL 하나만 있으면 된다"에서
"경로를 다룰 줄 알아야 한다"로 바뀌므로, 능력을 늘리지 않는다는 ADR-0005의 선을 건드린다. 그
선은 **필요해서** 그어진 것이 아니라 원칙으로 그어진 것이므로, 사용자의 결정이 필요하다.

## 결정 (지금)

**C를 고른다. 즉 지금은 구현하지 않는다.**

근거는 세 가지다.

1. **아직 문제가 되는 문서는 없다.** 실측이 확인한 것은 규모가 커지면 문제가 된다는 사실이지,
   지금 문제가 된다는 사실이 아니다. `e2e/large.spec.ts`가 다루는 2,000줄은 1.6 MB이고, GitHub
   케이던스로는 30초에 한 번 올라간다. 이 규모에서는 문제가 되지 않는다.
2. **A와 B와 D는 전부 문서로 못 박은 것을 되무는 일이다.** AGENTS.md의 작업 사이클이 "설계
   위반이 필요해 보이면 구현을 멈추고 DESIGN.md·ADR 쪽 논의로 돌아간다"고 지시한다. 이
   문서가 그 논의다.
3. **가장 싼 완화책은 사용자가 이미 가지고 있다.** 그것은 문서를 나누는 것이다. 폴더와 문서 간
   항목 이동이 이미 있으므로, 1만 줄짜리 문서 하나를 2,000줄짜리 문서 다섯 개로 나눌 수 있고,
   그러면 푸시 비용이 고친 문서의 몫으로 줄어든다. GitHub 백엔드에서는 이것이 곧 delta다.

## 언제 뒤집는가 — 미루기 위한 조건이 아니라 판정 기준

다음 중 하나가 참이 되면 이 결정을 다시 검토한다.

- 실제 워크스페이스에 **5,000노드를 넘는 문서**가 생기고, 그것을 나눌 수 없거나 나누고 싶지
  않을 때. (한 문서가 4 MB이고, GitHub의 30초 케이던스로 하루 종일 편집하면 업로드가 수 GB에
  이른다.)
- REST 백엔드를 상용하는데 **문서가 20개를 넘을 때.** 이 조건이 먼저 참이 된다.
- GitHub이 contents API 쓰기 요청을 크기 때문에 거절하기 시작할 때. (읽기는 blobs raw로 하므로
  1MB 상한이 적용되지 않지만, **쓰기 경로의 상한은 이 환경에서 문서로 확인하지 못했다**. egress
  제약 때문이다. 거절이 실제로 관측되면 그것이 1차 자료가 된다.)

**결정을 뒤집을 때는 D부터 검토한다.** 먼저 문제가 되는 쪽을 고치고, 그때 ADR-0005의 선을
"경로를 다룰 줄 아는 엔드포인트"까지 옮길지 판정한다.

## 지금 하지 않기로 한 것 중 기록해 둘 것

- **`children`을 원격에서 빼기**: 줄어드는 몫이 6.5%라서 할 만한 가치가 없다(위).
- **요청 압축**: 브라우저의 `CompressionStream`으로 gzip을 적용할 수는 있지만, 서버가 압축을 풀
  줄 알아야 한다. 기둥 2를 건드려야 하는데, 얻는 것은 delta보다 작다.
- **큰 워크스페이스에서 케이던스를 늦추기**: 크기에 따라 푸시 간격을 늘리면 업로드 총량은
  줄지만, 사용자가 잃는 것은 "다른 기기에서 언제 보이나"다. 문제를 옮길 뿐 해결하지는 않는다.
