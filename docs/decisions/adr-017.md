# ADR-017: 원격 저장소는 realtime보다 저비용 개인 sync를 우선한다

- 상태: 확정
- 결정: 중기 원격 sync는 항상 켜진 realtime stream보다 저비용 개인 다기기 sync를 우선한다.
- 이유: 제품 범위는 다중 사용자 공동편집이 아니라 개인 다기기 동기화다. 이 경우 초 단위 공동편집보다 앱 시작, 포커스 복귀, 수동 저장, 짧은 debounce window에서 안정적으로 최신 상태를 맞추는 것이 더 중요하다.
- 구현 상태: Phase 12-B에서 앱 런타임은 `RemoteStoreV2` snapshot-primary sync로 전환했다. v2 adapter는 최신 snapshot 1개를 primary artifact로 저장하며, write는 version/client 기반 compare-and-swap semantics로 처리한다. 충돌 시 밀려나는 로컬 snapshot은 conflict backup에 저장하고 `conflict` sync 상태로 사용자에게 알린다.
- 단기 방침: 기존 v1 Firebase RTDB append-log adapter는 legacy/migration 경계로 남긴다. 기본 앱 설정은 `?remote=firebase`가 명시되어도 v2 adapter를 만든다.
- 중기 방침: v2 snapshot-primary는 update log 저장량 폭증을 막는 안정화 단계일 뿐이다. 문서가 커진 뒤 한 글자만 수정해도 Firebase에는 전체 snapshot write/read가 발생할 수 있으므로, 다음 최우선 과제는 full-snapshot bandwidth 비용을 줄이는 저장소/프로토콜 재설계다.
- 우선 후보: 정적 snapshot/blob 중심 저장소, metadata-only conditional write, chunked snapshot, 또는 작은 delta를 별도로 다루는 서버/API 경계를 비교한다. Firebase RTDB realtime subscription은 비용 검증 전까지 기본 sync 방식으로 간주하지 않는다.
- 영향: Phase 12는 RTDB 최적화만으로 완료하지 않는다. 저장소가 바뀌어도 앱 런타임은 `RemoteStore` 인터페이스 뒤에서 동작해야 하며, import/export와 history 기능은 원격 저장소 구현에 직접 의존하지 않는다.
