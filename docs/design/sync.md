## 병합 모델 (DESIGN.md 원칙 3·4)

범용 CRDT 라이브러리를 얹는 대신, 아웃라인이 병합되기 위해 실제로 필요한 세 가지만 모델에
넣었다 ([ADR-0003](../adr/0003-custom-merge-model.md)):

1. **`parent` + `sort`** — 형제 순서를 배열이 아니라 노드마다 가진 분수 인덱스 키로 표현한다
   (`order.ts`). 두 기기가 같은 자리에 각각 줄을 넣어도 둘 다 남는다.
2. **내용과 위치를 따로 스탬프** — 한쪽에서 글을 고치고 다른 쪽에서 옮겨도 둘 다 반영된다.
   같은 필드의 동시 수정은 필드 단위 LWW로 한쪽이 이긴다 (의도된 한계).
3. **묘비(tombstone)** — 오래된 기기가 삭제된 줄을 되살리지 못한다. 단, 삭제 *이후에* 그 줄을
   고쳤다면 되살아난다. 묘비 보존은 30일 — 모든 기기가 같은 규칙으로 잊는다.

P0~P2 기능 확장(스키마 v6)이 병합 모델에 더한 것은 **규칙 하나뿐이다: `created`는 더 이른
쪽이 이긴다.** 나머지 새 필드(`checklist`/`numbered`/`color`/`bookmarked`/`quote`, 문서의
`parent`/`kind`/`query`/`deleted`)는 전부 기존 스탬프의 LWW를 탄다 — 총계는
[docs/parity.md](../parity.md) §7.

**단축키 표(v8)도 같은 LWW를 탄다.** 다만 판정 단위가 필드가 아니라 표 전체다 — 한쪽의
절반과 다른 쪽의 절반을 섞으면 누구도 고른 적 없는 표가 되기 때문이다. 표를 고른 적 없는
기기(`keymap: null`)는 고른 기기의 표를 빼앗지 않는다
([ADR-0008](../adr/0008-keymap-travels.md)). 화면 설정과 테마는 여전히 기기 로컬이다: 측정값은
화면의 것이고 단축키는 사람의 것이라는 것이 그 판정의 축이다.

폴더·저장된 검색·휴지통도 **전부 문서다** (DESIGN.md 원칙 15). `deleted` 스탬프가 붙으면
휴지통이고 파일은 그대로다 — 묘비는 내용을 안 들고 있어서(id와 시각뿐) 하드 삭제는 복구가
원리적으로 불가능한데, 소프트 삭제면 복구가 공짜다. 묘비 TTL이 지나면 진짜 삭제로 승격되고,
그 묘비는 **지금 시각으로** 찍는다 — 한 달 전 날짜로 찍으면 바로 다음 줄에서 잊혀지고, 파일을
아직 가진 기기가 문서를 되살린다.

병합은 `merge.ts`의 순수 함수 하나이고 순서 무관·멱등이다. 원격에서 새로 가져온 게 없으면
**같은 객체를 그대로 돌려준다** — 이 객체 동일성이 no-op 판별과 React 렌더 스킵의 근거다.
"두 기기가 각자 편집", "삭제가 되살아나지 않음", "서로를 서로의 자식으로 옮겨 생긴 순환
복구" 같은 실제 사고는 `sync/__tests__/merge.test.ts`가 고정한다.

## 전송 계약

계약은 **"버전 붙은 JSON을 읽고, compare-and-swap으로 쓴다"** 가 전부다. 쓰기가 지면
pull → merge → push를 재시도한다. 구현이 둘 있다:

- **아무 `GET`/`PUT` 엔드포인트** (Firebase RTDB 경로 포함). URL 하나가 계약이고 파일 하나
  통짜다.
- **GitHub contents API** — `GET`이 내용+`sha`를 주고 `PUT`이 그 `sha`를 요구하는 구조가
  계약과 정확히 일치해서, 낡은 `sha` 거부(409)가 기존 재시도 루프에 그대로 물린다. 푸시마다
  커밋이 생기므로 저장소 히스토리가 공짜 버전 아카이브가 된다.

케이던스는 백엔드마다 다르다:

| 백엔드 | 활동 중 | 유휴 | 비고 |
|---|---|---|---|
| REST | 1.5초 | 10초 | |
| GitHub | 10초 | 30초 | 커밋 소음·rate limit 고려. 조건부 GET — 304는 한도에 안 잡힌다 |

한 번의 푸시가 실제로 얼마인지는 재어 두었다 — 노드 하나가 약 800바이트이고, REST 백엔드는
워크스페이스 전체를 올리므로 문서가 늘수록 GitHub보다 먼저 아프다. delta 전송을 지금 하지
않기로 한 판정과 뒤집을 조건은 [ADR-0009](../adr/0009-delta-sync.md)에 있다.

원격이 이미 다 가진 상태에서는 푸시 자체를 건너뛴다(놀고 있는 기기가 빈 커밋을 남기지
않는다). 푸시 여부 비교는 **평문 직렬화**로 한다 (원칙 9). 같은 브라우저의 다른 탭도 병합
관점에서는 그냥 또 하나의 기기다.

## GitHub: 문서 하나 = 파일 하나

```
{폴더}/docs/{문서 id}.json   문서 하나 통째로 (폴더·저장된 검색·휴지통도 문서다)
{폴더}/graves.json           완전히 삭제된 문서의 묘비
{폴더}/keymap.json           고른 단축키 표 (고른 적 없으면 파일 자체가 없다)
{폴더}/files/{내용해시}.png  첨부
```

폴더 소속은 문서의 **필드**이지 경로가 아니다 — GitHub 레이아웃은 폴더가 생겨도 평평하다.

- **왜 쪼개나:** 파일 하나면 모든 커밋이 "전부 다시 씀"이라 히스토리가 무엇이 바뀌었는지
  말해주지 않는다. 쪼개면 푸시가 실제로 고친 문서만 싣고, 커밋 로그가 편집 로그가 된다.
- **바이트 안정 직렬화:** 키를 정렬해 들여쓴 JSON (원칙 13). 같은 내용이면 어느 기기가
  조립했든 바이트가 같아서 안 고친 문서는 커밋이 아예 안 생기고, 한 줄 편집이 diff에서 한
  줄로 보인다.
- **pull은 폴더 목록 조건부 `GET` 하나:** 목록이 주는 git blob `sha`가 곧 내용 해시라 `sha`가
  그대로인 문서는 받지도 않는다. 유휴 폴링은 304 두 번이고 rate limit에 잡히지 않는다.
- **여러 파일에 걸친 쓰기는 원자적일 필요가 없다.** 병합이 순서 무관이라 중간 상태를 읽은
  기기는 "어떤 기기가 가질 수 있었던 상태"를 볼 뿐이고 다음 주기에 수렴한다. 순서가 중요한
  지점은 단 하나 — **묘비를 먼저 쓰고 파일을 나중에 지운다** (원칙 8). 반대로 하면 중간에
  읽은 기기가 없는 파일을 "내가 올려야 할 문서"로 보고 되살린다.
- **문서를 넘나드는 항목 이동은 두 파일의 편집이라 순서 규칙이 하나 더 있다 — 묘비를 쓴
  문서를 먼저 푸시한다.** 반대면 중간에 읽은 기기가 같은 항목을 두 곳에서 본다. 데이터가
  깨지지는 않지만(다음 주기에 수렴한다) 그 창은 작을수록 좋다. 항목은 id를 그대로 들고
  간다 — `((id))` 링크가 살아야 하므로.
- 예전 단일 파일 레이아웃에서의 이행은 `sync/__tests__/github.test.ts`가 고정한다.

REST 백엔드는 파일 하나 그대로다 — 커밋 히스토리가 없으니 쪼갤 이유도 없다.

### 읽을 수 있는 Markdown 사본 (선택, 기본 꺼짐)

동기화 설정에서 켜면 문서마다 `{폴더}/markdown/{제목}.md`를 함께 커밋한다. 목적은 하나다:
**앱 없이 저장소만으로 노트를 읽는 것.** 결정은 [ADR-0007](../adr/0007-markdown-mirror.md),
불변식은 DESIGN.md 원칙 19, 파일 이름과 집합을 만드는 순수 함수는 `remote/mirror.ts`다.

- **파생물이고 입력이 아니다.** 앱은 이 파일을 읽지 않는다. 밖에서 고쳐도 반영되지 않고 다음
  저장에 덮어써진다. 그래서 손실이 있어도 된다 — 병합이 필요로 하는 스탬프·정렬 키·묘비는
  옆의 `.json`이 그대로 들고 있다.
- **암호와 배타다.** 암호가 걸리면 켜지지 않고, 이미 있는 사본을 **지운다.** 암호문 옆의
  평문은 암호를 건 의미를 없앤다. 판정은 UI가 아니라 `github.ts`의 `enabled`가 한다.
- **끄기는 수동적이지 않다.** 토글을 끄면 만들어진 사본을 지운다.
- **집합을 매번 다시 계산한다.** 무엇이 있었는지 기억하지 않으므로 오래 떨어져 있던 기기도 한
  번의 푸시로 수렴하고, 고아 파일이 남지 않는다.
- **이름은 제목에서 만들고 id는 파일 안에 넣는다.** 이름은 주소이고 id가 정체성이다. 제목이
  겹치면 문서 id 순으로 ` (2)`가 붙는다 — 모든 기기가 같은 답을 내야 하므로 정렬 기준이
  제목이 아니라 id다. 새 문서가 옛 이름을 가져갈 수 있다는 것이 그 대가이고, 알려진 한계다.
- **실패해도 문서 푸시를 막지 않는다.** 파생물이 없어지는 것은 읽는 사람의 편의를 잃는 일이지
  노트를 잃는 일이 아니다.
- **케이던스는 따로 없다.** 동기화 푸시를 타므로 10초와 30초이고, 편집 경로 바깥이다.

## 선택적 능력 — history와 files

백엔드의 `history`(커밋 읽기 → 문서 히스토리 뷰·복원)와 `files`(첨부)는 **전송 계약이 아니라
선택적 능력**이다 (DESIGN.md 원칙 17). 둘 다 GitHub 백엔드만 가진다 — URL 하나에는 옆에 둘
자리가 없고, 저장소에는 있다. 그게 두 백엔드의 실질적인 차이다.

- **히스토리 복원은 재스탬프한다** — 안 하면 다음 sync가 복원을 되돌린다 (undo와 같은 이유,
  원칙 10).
- **첨부**는 내용 해시로 이름 짓고(`sync/api/attachments.ts`) 1MB 상한(contents API가 그보다
  큰 파일의 바이트를 인라인으로 안 준다), E2EE가 켜져 있으면 노트와 같이 봉해진다.

## 종단 간 암호화 (선택)

암호를 넣으면 기기를 떠나기 전에 `PBKDF2-SHA256 → AES-GCM 256`으로 봉한다. 가능한 유일한
이유는 **병합이 클라이언트에 있어서다** — 서버가 판정하는 구조였다면 서버가 평문을 봐야 한다
([ADR-0002](../adr/0002-client-side-merge.md)).

- **salt는 별도 키 파일이 아니라 봉투 안에 들어간다.** 아무 파일이나 읽으면 유도 방법을 알 수
  있으니 "무엇을 먼저 읽어야 하나"가 없고 요청도 늘지 않는다. 두 기기가 빈 원격에서 각자
  암호를 걸면 salt가 둘 생기는데, 유도가 한 번 더 도는 것 말고는 아무 일도 없다 — 파일을 다시
  쓰면 쓴 쪽 salt로 조용히 정리된다.
- **읽지 못하는 상태(`locked`)는 실패와 구분한다** (원칙 7). 암호가 없거나 틀리면 푸시를 아예
  멈추고 배지에 그렇게 표시한다.
- 암호를 걸기 전에 쓰인 평문 워크스페이스는 그대로 읽히고, 다음 푸시에서 암호화된다.
- AES-GCM은 매번 새 IV를 쓰므로 같은 내용도 암호문은 매번 다르다 — 봉하는 건 (평문 비교로)
  쓰기로 결정한 다음이다.
- 봉투 왕복과 틀린 암호 거부는 `sync/__tests__/cipher.test.ts`가 고정한다.
